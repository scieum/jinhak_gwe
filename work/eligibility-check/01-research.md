# 01-research — 지원 자격 확인표 (eligibility-check, 학생)

작성일 2026-11-23 · 담당 researcher (S1)
근거: PRD 6-1 전형 상세 "지원자격(재학생 한정 여부, 학교장 추천 인원)", 8장 AdmissionProgram.eligibility(graduates_allowed, school_recommendation_limit), 13장(대학 공식 자료가 최종 기준 · NEVER-2).
앱 구현: `app/src/domain/planner.ts`(eligibilityStates · eligibilitySummary · newApplication · updateApplicationIdentity), `app/src/screens/Preparation.tsx`(view="eligibility"), `app/src/components/PlanEditor.tsx`, `app/src/components/Modal.tsx`. 메뉴 `shell/nav.ts` 학생 › "지원 자격 확인표"(아이콘 check). 진입 링크: 수시 입결 "지원 자격도 확인하기", 내 성적 추이 "지원 자격 확인표 열기", 원서·서류 체크리스트 "지원 자격 확인하기".

## 0. 이 화면이 하는 일 · 앱에 이미 있는 상태와 팝업

학생이 **직접 적는** 확인표예요. 대학 자료를 서비스가 판정하지 않아요. 상태 이름은 모두 "내가 확인한 기록"이에요(충족으로 확인 / 미충족으로 확인). 합격·지원 결과를 말하는 화면이 아니에요(NEVER-2). 계산 · 환산 숫자가 없어요(NEVER-1 해당 없음).

### 0-2. 항목 상태 (eligibilityStates) — S2 상태 프레임 후보

| 키 | 화면 이름 | 확인 기록 시각 |
|---|---|---|
| unknown | 확인 필요 | 없음 ("아직 확인하지 않음") |
| met | 충족으로 확인 | 저장 시각 기록 |
| unmet | 미충족으로 확인 | 저장 시각 기록 |
| na | 해당 없음 | 저장 시각 기록 |

전형 단위 요약 (eligibilitySummary): 확인 항목 없음 / 미충족 기록 있음(unmet 1개라도) / 확인 필요(unknown 1개라도) / 확인 기록 완료. 우선순위 = 미충족 > 확인 필요 > 완료.

## 1. 레퍼런스 (uibowl)

검색 8회, 모두 1페이지·국내 한정: 패턴 `체크리스트`(0건 — uibowl 패턴 이름 아님), 패턴 `자격 확인`, 컴포넌트 `체크박스 × 자격`, 컴포넌트 `리스트, 배지 × 신청하기`(0건), 컴포넌트 `바텀시트, 라디오 버튼`, OCR `삭제할까요 × 팝업`, 컴포넌트 `프로그레스 인디케이터, 체크박스`, 컴포넌트 `빈 화면 × 교육&도서`.
입시 지원 자격 확인표 자체는 0건이에요. 가장 가까운 건 대출 자격 확인(집지켜)이고, 나머지는 상태 고르기 · 진행 요약 · 삭제 확인 · 빈 화면 재료예요.

## 2. 반영 포인트

- P1: 항목 카드 = 조건 이름 + 아래 회색 부연 한 줄(메모 또는 안내 문구) 구조로 둬요. 기본 4항목은 이름 아래에 무엇을 확인하는지 짧은 부연을 붙여요(예: 학교장추천 필요 여부 → "추천 인원 · 학교 내 선발 일정"). 상태는 카드 오른쪽 위 한 곳에만 [근거: L1, L2, L8]
- P2: 상태 4종(확인 필요 / 충족으로 확인 / 미충족으로 확인 / 해당 없음)은 "판정 = 색 + 아이콘 + 이름" 규칙을 따르되, 학생이 적은 기록이라 될각 판정 색을 그대로 쓸지, data-status-badge 흑백 + 아이콘으로 할지 S2가 design.md 근거로 정해요. 어느 쪽이든 이름은 앱 문구 그대로("충족으로 확인") 써서 서비스 판정으로 읽히지 않게 해요 [근거: L2, L7, L8]
- P3: 상태 바꾸기·편집은 M2 자격 조건 확인 팝업 하나로: 맨 위 조건 이름 → 상태 4종을 세로 선택지 카드(선택된 것만 Selected 채움 + ✓) → 자료 링크 → 근거 메모 여러 줄 → 저장/취소. 상태 select를 선택지 카드로 펼쳐 한 번에 보이게 해요. PC modal, 모바일 bottom-sheet [근거: L3, L4, L5, L6]
- P4: 요약은 카드 하나로: "내 확인 상태" 요약 이름 + "확인 필요 n / 전체 m" 숫자. 진행 원형·퍼센트는 "완료"를 뜻해 오해가 생길 수 있어 숫자 두 개(stat-tile)까지만. Route Blue는 쓰지 않아요(내 위치 화면이 아님) [근거: L7, L9]
- P5: 자료 링크는 카드 오른쪽 끝 "등록한 자료 열기 ↗" 텍스트 링크로, 없으면 회색 "자료 링크 미등록". 원문 확인이 행동의 중심이라 메모보다 아래로 내리지 않아요 [근거: L8, L1]
- P6: 삭제 확인(M3 · M4)은 제목 질문 + 함께 지워지는 것 설명 한 줄 + 취소 / 삭제 2버튼. 삭제는 button-danger-text 규칙(확인 모달 필수)에 맞춰 위험 글자 버튼으로, 주요 버튼 채움은 쓰지 않는 안을 S2에서 검토해요(지금 앱은 삭제가 ButtonPrimary) [근거: L10, L11, L12]
- P7: M1 전형 추가/수정은 "등록된 전형에서 선택"을 맨 위에 두고 직접 입력을 아래로. 정체성(학년도·대학·전형·모집단위) 변경 경고와 중복 안내는 입력칸 아래 안내 줄로, 중복이면 주요 버튼 이름이 "기존 준비 기록 열기"로 바뀌는 상태 프레임을 따로 그려요 [근거: L6, L9]
- P8: 전형이 없을 때는 empty-state(선 아이콘 + 제목 + 설명 + "지원 전형 추가" 버튼 하나). 앱은 버튼이 머리에만 있으니 empty-state 안에도 하나 두는 안을 S2가 결정. 항목을 모두 지운 전형은 목록 자리에 "확인 항목이 없어요 · + 자격 조건 추가" 한 칸 [근거: L13, L14]
- P9: 안내 · 고지는 목록 위 회색 notice 한 덩어리로 유지: "직접 작성하는 확인표예요 · 최종 지원 자격은 학교·대학에 확인해요". 합격·지원 결과를 말하는 문장은 넣지 않아요 [근거: L1, L7]

## 4. S2 주의 · 미결

1. **rules/design-rules.json `screens`에 `eligibility-check`가 없어요.** G2 · G3 · judge가 slug를 못 찾을 수 있어요. rules/는 사람만 고칠 수 있으니 오케스트레이터가 사용자에게 등록을 요청해야 해요. `requires_disclaimer_note` · `requires_trace_accordion` 목록에도 없어요(계산이 없으니 trace는 불필요로 보임).
2. 상태 색: 수능 최저 배지는 judge 색 쌍을 재사용하지만(design.md), 이 화면은 학생 자가 기록이에요. judge 색을 쓰면 서비스 판정으로 읽힐 수 있어 흑백 + 아이콘 + 이름 안도 함께 검토해 주세요. 새 토큰 · 새 컴포넌트가 필요하면 멈추고 "design.md 수정 제안".
3. 상태 선택지 카드(P3)가 design.md 기존 컴포넌트(segmented-control, filter-chip, 라디오 없음)로 표현되는지 확인 필요. 안 되면 select(드롭다운) 그대로.
4. 삭제 버튼 위계: 앱은 확인 모달의 "삭제"가 ButtonPrimary예요. design.md button-danger-text와 맞출지 S2 결정(앱 코드 수정은 이 하네스 범위 밖).
5. 이동 링크 5개가 전형 카드 안에 button-outline로 쌓여 있어요. 모바일 390에서 줄바꿈 처리(가로 스크롤 vs 접기)를 정해야 해요.
6. 0-5의 "전형계획 데이터로 미리 채우기"는 검수 데이터 연결이 필요해요. 그린다면 data-status-badge(모집요강 반영 · 기준일)와 원문 쪽수를 함께 둬야 해요.
7. uibowl 한계: 입시 · 교육 앱의 지원 자격 확인 화면은 0건이에요. 상태 4종 카드 목록 화면도 직접 사례가 없어 대출 자격 확인(L1, L2) · 약관 동의(L8) 구성을 빌렸어요.
